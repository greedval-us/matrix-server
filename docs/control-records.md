# Таблица control и вкладка «Записи»

`control` — рабочая таблица в MySQL 8.4 контейнера `mysql`, база `matrix`.
Миграция `002_control.sql` создаёт таблицу, а `003_control_initiator.sql` добавляет
поле «Инициатор» перед «Исполнитель» без изменения существующих данных. Для старых
записей оно остаётся NULL. Миграции применяются командой `npm run migrate` или
Compose-сервисом `migrate` и не обращаются к исходной MariaDB.
Таблица не включается в Manticore и не является каталогом `data_base`.

| Колонка клиента | Поле MySQL | Значение |
| --- | --- | --- |
| Дата | `date` | Календарная дата, по умолчанию текущая дата MySQL |
| ID | `id` | Автоматический BIGINT UNSIGNED; в API строка без потери точности |
| Номер | `number` | Строка; сохраняет ведущие нули и знак `+` |
| ФИО | `fio` | Текст |
| Дата рождения | `date_of_birth` | Календарная дата или NULL |
| Инициатор | `initiator` | Необязательное текстовое имя, до 255 символов |
| Исполнитель | `executor` | Текстовое имя |
| Примечание | `note` | Текст |
| Реализация | `realization` | Текст |
| Пересечения | `intersections` | Текст, без автоматического поиска связей |
| Файлы | `files` | JSON-массив подтверждённых метаданных вложений |

Даты передаются как `YYYY-MM-DD`; пустая дата преобразуется в NULL. Отсутствующее
поле даты при создании использует значение по умолчанию. Файловый столбец нельзя
переписать обычным обновлением записи: он изменяется только файловыми RPC.

## API

Модуль `records`, контракт `protos/records.proto`, сервис
`matrix.records.v1.Records` работает на том же gRPC endpoint/TLS.

- `GetCapabilities`, `ListRecords`, `CreateRecord`, `UpdateRecord`, `DeleteRecord`,
  `UploadFiles`, `DownloadFile`, `RemoveFile` используют обычный клиентский
  `MATRIX_API_KEY`. Ответ capabilities сообщает поддержку создания, изменения,
  удаления записей и операций с файлами.
- Вкладка позволяет создавать и изменять девять полей записи: `date`, `number`,
  `fio`, `date_of_birth`, `initiator`, `executor`, `note`, `realization`, `intersections`.
  Сервер назначает `id`; метаданные `files` изменяются только файловыми RPC.
- Поиск, сортировка и подсчёт применяются в MySQL до пагинации. Поля сортировки
  строго перечислены; ID дополнительно стабилизирует порядок. Поиск — буквальная
  подстрока, символы `%` и `_` не превращаются в SQL-маски.

Пример тела `CreateRecord` для клиента:

```json
{"values":{"date":"2026-11-05","number":"001234","fio":"Тестовая запись","date_of_birth":"1990-01-01","initiator":"Инициатор","executor":"Исполнитель","note":"Примечание","realization":"В работе","intersections":"Уточняются"}}
```

Пример `ListRecords` для обычного клиента:

```json
{"query":"001234","sort_key":"date","sort_direction":"desc","page":1,"page_size":25}
```

Создание допускает незаполненные описательные поля. Обновление меняет только
переданные поля. Пустая строка очищает «Инициатор»; NULL из MySQL возвращается
клиенту как пустая строка. Инициатор участвует в поиске и сортировке вместе с
остальными полями. ID и метаданные файлов доступны только для чтения. Удаление строки
с вложениями отклоняется: сначала требуется удалить её вложения.

## Файлы

Метаданные содержат UUID, имя, размер и MIME-тип. Содержимое хранится по UUID в
`MATRIX_RECORDS_FILE_DIR`, в Compose это `/var/lib/matrix/files` и постоянный
named volume `control-files`. Только API монтирует этот том. Пути сервера не
передаются клиенту и не используются как имена загружаемых файлов.

Один файл ограничен 25 МиБ, пачка — 20 файлами и 100 МиБ; блоки до 64 КиБ. В пачке
разрешена одна запись. Метаданные публикуются вместе после успешного приёма всей
пачки. Ошибка передачи и подтверждённый откат до попытки COMMIT удаляют файлы пачки.
При потере соединения во время публикации метаданных сервер сохраняет содержимое
до согласования итогового состояния БД, чтобы не удалить файл при позднем успешном COMMIT. Обычное чтение
снимка не доказывает откат ещё завершающейся транзакции.

Скачивание и удаление проверяют пару `row_id/file_id`: UUID другой записи не даёт
доступа к ней. При удалении сначала подтверждается изменение метаданных, затем
удаляется содержимое. Ошибка очистки фиксируется без персональных данных;
недоступный через API остаточный файл требует уборки при обслуживании. Резервная
копия должна согласованно сохранять MySQL `matrix` и том `control-files`.

## Клиент и развёртывание

В production вместо заглушки подключён main-process gRPC-репозиторий. Он использует
текущие настройки сервера, доверенный сертификат и API-ключ из «Настроек».
Административный ключ для вкладки не нужен. Десять полей выводятся в заданном
порядке и дополняются готовой колонкой «Файлы»; формы изменяют девять рабочих полей,
а удаление доступно для записей без вложений. Доступа к MySQL из Electron нет.

Compose включает `records` и постоянный том, доступный пользователю `node` образа
API. На будущем Docker-сервере примените миграции перед обновлением API, затем
проверьте пустую вкладку, создание тестовой записи и цикл загрузки/скачивания/
удаления файла. TLS и доверенный сертификат настраиваются по `deployment.md`.
Локальная подготовка включает unit/loopback gRPC проверки и сборку клиента,
без запуска Docker, реальной миграции или изменений исходных данных.
