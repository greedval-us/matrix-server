# Публикация приложения для клиентов

Модуль `releases` отдаёт клиенту последнюю опубликованную сборку для его платформы,
архитектуры и формата через существующее соединение gRPC. Используются тот же TLS,
ключ доступа и, при `MATRIX_AUTH_MODE=device`, подпись устройства. Административный
ключ для скачивания не нужен. Метаданные и файлы находятся в каталоге сервера;
таблицы и миграции БД для релизов не добавляются.

Поддерживаются Windows `win32` / `x64`, `arm64`, `ia32` / `portable` и Linux
`linux` / `x64`, `arm64` / `appimage`. Версия — стабильная `x.y.z` без префикса `v`,
ведущих нулей и суффиксов; каждая часть содержит не более девяти цифр. Размер
сборки — от 1 байта до 2 GiB. Клиент Windows получает portable EXE; клиент Linux —
AppImage. Публикуйте файл, собранный для выбранной архитектуры: издатель проверяет
целостность и метаданные, но не исполняет и не анализирует машинный код приложения.

## Настройка сервера

В native-окружении задайте:

```dotenv
MATRIX_MODULES=search,catalog,workspace,records,releases
MATRIX_RELEASES_DIR=/var/lib/matrix/releases
```

Сохраните уже используемый список модулей, добавив `releases`. По умолчанию новый
сервер включает `search,catalog,releases`, а каталог — `data/releases`. Для режима
без MySQL достаточно `MATRIX_MODULES=releases` и существующего общего ключа.
Пустой или ещё отсутствующий каталог допустим: запрос версии вернёт `NOT_FOUND`.
После изменения списка модулей или пути перезапустите API; публикация следующих
сборок перезапуска не требует.

В Compose модуль уже включён. Том `client-releases` подключён к API только для
чтения в `/var/lib/matrix/releases`. При использовании `compose.storage.yaml`
он хранится в `${MATRIX_DATA_ROOT}/client-releases`. До запуска обновлённого API
создайте каталог на том же диске данных, где находятся остальные тома:

```bash
sudo install -d -o 1000 -g 1000 -m 0750 "$MATRIX_DATA_ROOT/client-releases"
```

Контейнеры работают от UID/GID 1000. Каталог должен разрешать этому пользователю
чтение, а одноразовому издателю — запись. Используйте обычный локальный каталог
без символических ссылок или junction в его пути. Для native-развёртывания
выберите владельца/группу пользователя API и издателя. Каталог не должен быть
доступен на запись клиентам или другим непривилегированным пользователям.

## Загрузка файла и явная публикация

Сначала соберите нужную версию клиента и перенесите файл на сервер своим обычным
каналом администрирования, например SCP. Сам API не принимает публикации от
клиентов и не предоставляет загрузку файлов релиза через сетевой RPC.

Для native-сервера с Node.js 24 из корня репозитория:

```bash
npm run release:publish -- \
  --file /srv/matrix/upload/Matrix.exe \
  --directory /var/lib/matrix/releases \
  --version 1.2.3 --platform win32 --arch x64 --kind portable \
  --notes "Исправления поиска и интерфейса"
```

`--directory` можно опустить при настроенном `MATRIX_RELEASES_DIR`. Команда npm
загружает локальный `.env`, если он существует. Издатель не подключается к MySQL
или API и не требует ключа доступа. Для другой архитектуры меняйте `--arch`; для
Linux используйте `--platform linux --arch x64 --kind appimage` и путь AppImage.

Для Compose используйте функцию `matrix_compose` из
[инструкции выкладки](deployment.md#подготовка-и-tls), чтобы выбрать те же проект,
файлы Compose и окружение, что использует API. `$UPLOAD` — существующий абсолютный
каталог с загруженным файлом на Docker-хосте, доступный UID 1000 для чтения:

```bash
UPLOAD=/srv/matrix/upload
matrix_compose --profile tools run --rm --no-deps \
  --volume "$UPLOAD:/upload:ro" release-publish \
  --file /upload/Matrix.exe \
  --version 1.2.3 --platform win32 --arch x64 --kind portable \
  --notes "Исправления поиска и интерфейса"
```

Сервис `release-publish` использует образ API с явной командой издателя, отдельное
подключение тома на запись и отключённую сеть. После обновления исходников сначала
пересоберите образ API согласно процедуре выкладки. Обычный запуск API не выполняет
публикацию.

Издатель печатает только итоговые публичные метаданные: версию, платформу,
архитектуру, формат, имя скачиваемого файла, размер, SHA256, время и примечания.
Сверьте версию и SHA256 с ожидаемой сборкой. Уже запущенный клиент увидит обновление
при следующей проверке; новый файл проверяется клиентом по размеру и SHA256 до
предложения запуска.

## Целостность и смена версии

Издатель копирует исходный файл во временный файл этого же каталога, вычисляет
SHA256 и проверяет размер и изменение исходного файла. Полный файл синхронизируется
на диск и публикуется под именем, содержащим версию, цель и SHA256. Имя артефакта
никогда не перезаписывается. Затем атомарно заменяется `manifest.json`. Доступна
только полная сборка, на которую указывает завершённый манифест.

Каталог должен поддерживать жёсткие ссылки и атомарное переименование в пределах
одной файловой системы, например NTFS/ext4. Одна публикация блокирует каталог через
`.publish.lock`; параллельная команда завершится ошибкой. После аварийного завершения
процесса проверьте отсутствие действующего издателя, затем удалите оставшуюся
блокировку вручную. Не удаляйте блокировку во время публикации. Временные файлы и
артефакты, не упомянутые в манифесте, можно убрать отдельно после этой проверки.

Для каждой цели хранится одна последняя версия. Понижение версии запрещено.
Повторная публикация той же версии с теми же байтами возвращает прежние метаданные;
с другими байтами завершается ошибкой. Для исправленной сборки или изменённых
примечаний используйте новую версию. Старые артефакты сохраняются на диске; удаляйте
их только после завершения старых загрузок. Резервируйте каталог вместе с
`manifest.json`. При переносе сохраняйте содержимое и права доступа.

Не редактируйте manifest вручную и не меняйте опубликованные файлы. Неверные
размеры, имена, пути, хеши, ссылки или превышение лимитов приводят к отказу выдачи.
Хеш потока проверяется также на сервере. Манифест ограничен 64 KiB, примечания —
8000 байт UTF-8. Дистрибутивы и runtime-манифест остаются вне Git и образа приложения;
каталог `data/` и файлы EXE/AppImage уже исключены правилами публикации.

## Контракт gRPC

Контракт находится в `protos/releases.proto`, сервис — `matrix.releases.v1.Releases`.

- `GetLatest({platform, arch, kind})` возвращает `Release`: `version`, `platform`,
  `arch`, `name`, `size:uint64`, `sha256`, `published_at`, `kind`, `notes`.
- `Download({platform, arch, kind, version, sha256})` возвращает первый кадр
  `release` с теми же метаданными, затем кадры `data` не более 256 KiB каждый.
  Клиент должен проверить метаданные первого кадра, количество байт и SHA256.
- `NOT_FOUND` означает отсутствие релиза для цели или смену последней версии между
  проверкой и загрузкой; в последнем случае запросите версию снова. Если модуль
  выключен, сервер вернёт `UNIMPLEMENTED`. Неверная цель — `INVALID_ARGUMENT`,
  повреждённый манифест/артефакт — `FAILED_PRECONDITION`.

Оба вызова проходят существующую авторизацию и журналирование. Подпись устройства
использует точные пути `/matrix.releases.v1.Releases/GetLatest` и
`/matrix.releases.v1.Releases/Download`. Передача учитывает backpressure и закрывает
файл при отмене; весь дистрибутив не загружается в память.

Проверки: `node --test tests/releases.test.mjs tests/releases-grpc.test.mjs
tests/config.test.mjs`, затем `npm test` и `npm run check:publication`.
