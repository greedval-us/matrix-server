# Будущая выкладка Matrix

Инструкция для оператора будущего Linux Docker-хоста. Команды запуска ниже нужно
выполнять на этапе выкладки; при разработке они не выполняются. На этом этапе
проверяется только конфигурация Compose без запуска daemon, контейнеров или доступа
к исходному серверу. Нужны Docker Engine с Compose v2, место под индексы и доступ к исходной
MariaDB из явно запускаемых задач.

## Роли, данные и сеть

| Роль | Назначение | Секреты и доступ |
| --- | --- | --- |
| `mysql` | MySQL 8.4, БД `matrix` | Операционный и root-пароли; порт не опубликован |
| `migrate` | `node scripts/migrate.mjs`, однократная миграция | Только операционная MySQL |
| `api` | Node.js 24, `search,catalog,workspace,records` | Операционная MySQL, два API-ключа, TLS, вложения `control` |
| `manticore` | Поиск по готовым индексам | Без исходных DB-паролей; порты не опубликованы |
| `indexer` | Профиль `indexing`, явная сборка | SELECT источника, операционный каталог |
| `catalog-copy` | Профиль `tools`, явное копирование каталога | SELECT источника, INSERT в пустой каталог |

`backend` — внутренняя сеть. У API есть отдельная сеть `edge`, необходимая для
публикации host-порта; исходные credentials в API отсутствуют. Только opt-in задачи
имеют сеть `source` для маршрута к исходному серверу. Это не заменяет права БД:
исходный пользователь должен иметь только SELECT на нужные таблицы.
Задайте реальный адрес в обязательной переменной `SOURCE_MYSQL_HOST`, а имя БД —
в `SOURCE_MYSQL_DATABASE`. `source-db` и `source_data` в примере являются заменителями.
Не используйте `127.0.0.1` для базы на другом хосте.

Порядок запуска: здоровая MySQL → успешная `migrate` → API. API также ждёт здоровую
Manticore. MySQL healthcheck проверяет авторизованный SELECT, Manticore — HTTP SQL
`SHOW TABLES`, API — доступность TCP transport. Прикладные gRPC-проверки описаны ниже.
Условия зависимостей описаны в [документации Compose](https://docs.docker.com/compose/how-tos/startup-order/).

## Подготовка и TLS

1. Скопируйте `.env.compose.example` в `.env` на будущем хосте. Замените все пароли
   и ключи уникальными значениями. Ограничьте доступ к `.env` (`chmod 600 .env`).
   Compose подставляет только явно перечисленные переменные каждого сервиса;
   файл целиком в API не передаётся. Команда `config` без `--quiet` выводит секреты.
2. В примере host bind — `127.0.0.1:50051`, TLS отключён для проверки на localhost.
   Перед LAN-доступом получите серверный сертификат с SAN для реального имени/IP.
   Поместите `server.crt`, `server.key` в `MATRIX_TLS_DIR`; этот существующий каталог
   монтируется read-only в `/run/matrix/tls`. Автоматической генерации сертификата нет.
3. Установите `MATRIX_GRPC_TLS_CERT=/run/matrix/tls/server.crt` и
   `MATRIX_GRPC_TLS_KEY=/run/matrix/tls/server.key`, затем
   `MATRIX_BIND_HOST=<LAN-IP-сервера>`. Обе TLS-переменные задаются вместе.
   API работает как `node` uid/gid 1000: на Linux подойдут владелец `root:1000`,
   каталог 0750 и ключ 0640. Проверьте фактическую доступность файлов из контейнера.
4. Передайте клиентам доверенный CA или публичный сертификат, адрес и поисковый
   ключ. Административный ключ предназначен только для административного клиента.
   Приватный TLS-ключ остаётся на сервере. Ограничьте gRPC LAN/VPN и firewall.

`MATRIX_API_KEY` и `MATRIX_ADMIN_API_KEY` должны отличаться. В первой схеме миграция
и API используют одного операционного пользователя; это не пользователь источника.
Для разделения привилегий при эксплуатации можно подготовить отдельные учётные
записи миграции и чтения каталога с соответствующей настройкой Compose.

Node-клиент MySQL передаёт пароль точно, включая пробелы. При `_PASSWORD_FILE`
удаляется только завершающий перевод строки; не задавайте одновременно значение
пароля и его `_FILE`. Индексатор записывает подключения в Manticore-конфигурацию
и отклоняет управляющие символы, `#`, `{`, `}`, обратную косую черту и пробелы по
краям вместо их экранирования. Это относится и к исходным, и к каталожным DB-настройкам.
Для него доступны `SOURCE_MYSQL_PASSWORD_FILE`/`MYSQL_PASSWORD_FILE` и
`CATALOG_MYSQL_PASSWORD_FILE`: снимаются только завершающие CR/LF, прочие символы
сохраняются и проходят ту же проверку. В текущем Compose используются переменные
паролей; переход на файлы требует их явного подключения к нужным сервисам.

MySQL создаёт БД/пользователя только на пустом data-volume. Изменение пароля в `.env`
не меняет пароль существующего пользователя: ротацию выполняют отдельно в MySQL и
затем обновляют настройки. См. [инициализацию официального образа MySQL](https://github.com/docker-library/docs/blob/master/mysql/README.md#environment-variables).

## Первый старт

На будущем хосте после настройки секретов и TLS:

```bash
docker compose config --quiet
docker compose build api migrate manticore indexer catalog-copy
docker compose up -d
docker compose ps -a
docker compose logs --tail=100 migrate api manticore
```

`migrate` должен завершиться с кодом 0. Он применяет версии из `migrations`, повторный
запуск пропускает уже применённые версии. После изменения схемы/образа явно выполните
`docker compose run --rm migrate` перед обновлением API. Ошибка миграции блокирует
зависимый API; не обходите её ручным запуском процесса сервера.

Manticore-entrypoint готовит каталоги томов и при отсутствии активной конфигурации
вызывает `--bootstrap`. Bootstrap создаёт пустую поисковую конфигурацию без DB-доступа
и исходных credentials, затем запускает `searchd` от пользователя `manticore`.
Существующая активная конфигурация при перезапуске сохраняется. Обычный `up` не
активирует профили `indexing`/`tools` и не выполняет копирование или построение шардов.

Первый старт с пустым `data_base` допустим. Каталог/рабочие таблицы можно проверять
административным RPC, но это ещё не проверка поиска по исходным данным.

## Копирование только каталога

Подготовьте SELECT-пользователя на источнике и задайте `SOURCE_MYSQL_*` в `.env`.
Проверьте правильность пары: настроенный источник, например `source-db/source_data`,
и операционная цель `mysql/matrix`.
После миграции явно выполните:

```bash
docker compose run --rm catalog-copy
```

Задача запускает `node scripts/copy_catalog.mjs` в Node-образе с отдельным окружением.
Она читает только перечисленные поля `data_base` через SELECT, сохраняет исходные
ID и отказывается работать с непустым целевым `data_base`. Источник не изменяется.
Копирование не переносит исходные таблицы, полный dump MariaDB, рабочие таблицы или
логи. Идентификатор документа Manticore включает ID каталога, поэтому перенумерация
каталога недопустима при сохранении индексов.

При повторном запуске с непустой целью ожидается отказ. Не очищайте действующий
каталог ради повторного импорта: сначала определите процедуру согласованного
обновления каталога и индексов и сохраните резервную копию.

Для локального Node-запуска вне Compose аналогичная явная команда —
`npm run catalog:copy` после `npm run migrate`; обе читают `.env`, если он существует.
Для источника задайте отдельные `SOURCE_MYSQL_*`, для цели — `MATRIX_MYSQL_*`.

## Административный CRUD

Контракт `protos/workspace.proto` описывает сервис `matrix.workspace.v1.Workspace`.
Методы: `ListRows`, `GetRow`, `CreateRow`, `UpdateRow`, `DeleteRow`. Передавайте
административный ключ в metadata `x-api-key` из защищённой настройки клиента;
не помещайте ключ в аргументы командной строки или JSON запроса. Поисковый ключ
для этих методов не подходит.

`resource` допускает только `data_base`, `work_items`, `service_logs`. `Row` имеет
`id:string` и `values:map<string,string>`: даже числа, флаги и JSON передаются строками.
`ListRows` возвращает `rows` и `total:string`; `limit` по умолчанию 100, максимум 1000,
`offset` — `uint32`. Например, тела последовательных запросов для рабочей записи:

```json
{"resource":"work_items","values":{"namespace":"review","name":"batch-1","payload":"{\"status\":\"new\"}"}}
```

Это `CreateRow`; сохраните `id` из ответа. С ним можно вызвать `GetRow`:

```json
{"resource":"work_items","id":"123"}
```

И `UpdateRow`:

```json
{"resource":"work_items","id":"123","values":{"payload":"{\"status\":\"reviewed\"}"}}
```

Для `DeleteRow` используется такое же тело, как для `GetRow`; ответ содержит
`deleted:boolean`. Для `ListRows`:

```json
{"resource":"work_items","limit":100,"offset":0}
```

У `work_items` обязательны непустые `namespace` и `name`; `payload` содержит
сериализованный JSON, при отсутствии получает `{}`. Поля `data_base` перечислены
в `CATALOG_FIELDS` (`node/modules/workspace/resources.mjs`) и соответствуют каталогу
источника. `id` и `name_table` неизменяемы через `UpdateRow`.

Непустой опубликованный `database-catalog.json` резервирует ID баз этой генерации:
удаление или повторное создание записи с таким ID возвращает
`FAILED_PRECONDITION`. После публикации создание любой новой `data_base` требует
явного незарезервированного `id`, чтобы автоинкремент не переиспользовал идентичность.
Метаданные существующей записи редактировать можно; замороженный поисковый снимок
и план индексирования от этого автоматически не обновляются.

`service_logs` поддерживает только `ListRows`/`GetRow`. Сервер пишет метаданные
запросов: `module`, `method`, `status_code`, `duration_ms`, `created_at` (и ID строки).
Содержимое исходных строк, payload запросов и API-ключи в этот журнал не записываются.

## Явная индексация и восстановление

Проверьте каталог и источник перед дорогой операцией, затем запустите одну задачу:

```bash
docker compose run --rm indexer python3 /app/scripts/build_manticore_indexes.py --help
docker compose run --rm indexer python3 /app/scripts/build_manticore_indexes.py --check-config
docker compose run --rm indexer
```

Аргументы `run` заменяют весь command сервиса. `--check-config` требует доступного
каталога/источника и проверяет конфигурацию следующего шарда; это не пробная полная
индексация. Не запускайте `--profile indexing up` как обычный старт: этот профиль
специально включает дорогое построение. Не включайте оба профиля через
`COMPOSE_PROFILES` для повседневного `up`.

Индексатор читает каталог из `CATALOG_MYSQL_*` (`matrix`), исходные строки — из
`MYSQL_*`, которым Compose подставляет `SOURCE_MYSQL_*`. При прямом Python-запуске
поддерживаются также aliases `SOURCE_MYSQL_*`. Только исходные таблицы, на которые
ссылается `data_base`, участвуют в плане; операционные `work_items`/`service_logs`
не перечисляются и не индексируются.

После проверки шарда `indextool` индексатор обновляет активную конфигурацию,
перезагружает таблицы SQL-запросом через `http://manticore:9308` и ждёт фактической
видимости таблиц. PID namespace, PID-файл и Docker socket с ним не разделяются.
После остановки повторите `docker compose run --rm indexer`: готовые шарды и точка
продолжения сохраняются, незавершённый шард будет повторён. Не удаляйте runtime-данные
и не меняйте идентичность каталога при восстановлении.

После первого построения `index-plan.json` и `database-catalog.json` остаются
замороженными для этой генерации. Добавление или удаление базы в операционном
`data_base` не добавляет/исключает её автоматически из уже созданного плана, а
изменение описаний не обновляет поисковый снимок. Планируйте такие изменения как
отдельное обслуживание: сохраните согласованный backup, подготовьте новую генерацию
или полную переиндексацию с сохранением ID, проверьте её и согласованно переключите
каталог/индексы. Обычное возобновление выполняет прежний план. Очистка действующей
генерации не является рутинным способом обновления каталога.

## Тома и резервные копии

| Named volume | Путь | Кто использует |
| --- | --- | --- |
| `mysql-data` | `/var/lib/mysql` | MySQL |
| `control-files` | `/var/lib/matrix/files` | Только API; содержимое вложений `control.files` |
| `manticore-config` | `/var/lib/manticore/config` | Manticore, indexer; активный `manticore.conf` |
| `manticore-state` | `/var/lib/manticore/state` | Публичные JSON; API только read-only |
| `manticore-indexes` | `/var/lib/manticore/indexes` | Manticore, indexer |
| `manticore-runtime` | `/var/lib/manticore/runtime` | Только Manticore, включая PID |
| `manticore-log` | `/var/lib/manticore/log` | Manticore, indexer |
| `manticore-private` | `/var/lib/manticore/private` | Только indexer; конфигурация с исходным паролем |

Публичные файлы state имеют права 0644, каталоги 0755 — Node uid 1000 может читать
их независимо от UID Manticore. Private-каталог имеет права 0700, секретные файлы
0600. API не монтирует config/private/indexes/runtime/log. Entry point меняет права
только корней томов; восстановленные файлы должны сохранять владельца Manticore и
права. Не исправляйте доступ через `chmod -R 777`.

Оба Manticore-роли используют один Dockerfile-stage на
`manticoresearch/manticore:29.9.0`, чтобы `searchd`, `indexer`, `indextool` совпадали.
Версия соответствует [официальному Dockerfile](https://github.com/manticoresoftware/docker/blob/master/Dockerfile)
на момент подготовки. Перед выкладкой проверьте доступность тега/архитектуры;
обновляйте и проверяйте обе роли вместе. Для воспроизводимой production-сборки
после проверки можно закрепить digest. Базовый образ объявляет `/var/lib/manticore`
как volume; persistent-данные приложения перечислены выше, дополнительные файлы
в корне этого каталога не считаются частью резервной копии.

Для бэкапа остановите indexer и API-запись, сделайте согласованный логический dump
MySQL `matrix` через `mysqldump` из контейнера. Сохраните том `control-files` вместе
с дампом MySQL: оба нужны для восстановления вложений. Затем остановите Manticore и сохраните
config/state/indexes вместе, сохраняя владельцев и права; отдельно сохраните TLS,
`.env` и при необходимости private-конфигурацию в защищённом хранилище. Не включайте
исходную MariaDB в перенос операционной БД. Логи храните по своей политике retention.
Проверьте восстановление на отдельном хосте с той же версией Manticore. `down`
сохраняет named volumes; `down -v` уничтожает их и не является обычной остановкой.

## Проверки при выкладке

До запуска daemon локально доступны:

```bash
npm test
python3 -m unittest discover -s tests
docker compose --env-file .env.compose.example config --quiet
docker compose --env-file .env.compose.example --profile indexing --profile tools config --quiet
```

На будущем хосте дополнительно проверьте сборку обоих образов, совпадение версий
Manticore tools/daemon, миграцию на пустой MySQL и повторный запуск, TLS handshake,
gRPC с поисковым/административным ключами и отказ workspace для поискового ключа.
Для существующего поискового smoke-клиента задайте `MATRIX_API_KEY`,
`MATRIX_GRPC_TLS_CA` и запустите
`node scripts/check_grpc.mjs --endpoint <имя-из-сертификата>:50051`.
После явной индексации проверьте поиск, отмену, статус и сохранение шардов после
перезапуска. Проверьте отсутствие published-портов MySQL/Manticore и доступность
только нужного gRPC bind. Эти live-проверки не заменяются успешным `compose config`.

## Расширение API

Таблица `control` и подключение вкладки «Записи» описаны в
[control-records.md](control-records.md). Миграция `002_control.sql` создаёт все
запрошенные поля; содержимое вложений хранится в отдельном постоянном томе API.

Добавляйте функциональный модуль в `node/modules/<name>` с явной регистрацией через
`register(context)` и собственным ID; подключайте его в едином реестре
`node/modules/index.mjs`, используемом приложением и проверкой конфигурации, затем
добавляйте ID в `MATRIX_MODULES`.
Общие настройки, авторизация и завершение остаются в `node/core`. Публичный контракт
описывайте в protobuf, сохраняя совместимость search/catalog. Новую роль авторизации
проверяйте реальными loopback gRPC-тестами.

Для нового CRUD-ресурса создайте версионированную миграцию и статическое описание
допустимых полей в `node/modules/workspace/resources.mjs`; отделите читаемые и
записываемые поля. При необходимости расширьте валидацию значений и преобразование
строк в `node/infrastructure/mysql/repository.mjs` и добавьте проверки контракта.
Используйте параметризованные запросы репозитория, а не имена таблиц/колонок из
клиентского ввода. Логи остаются append-only для сервера. Добавление операционной
таблицы не даёт ей право участвовать в индексации: индексатор работает только с
явно описанными в каталоге исходными таблицами.
