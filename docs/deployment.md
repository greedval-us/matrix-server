# Разработка и выкладка Matrix

Локально разрабатывают и проверяют переносимые исходники. Установку, настройку TLS,
подготовку дисков и запуск выполняют на Linux Docker-хосте. Для этого нужны Docker
Engine с Compose v2, место под индексы и доступ к исходной MariaDB из явно
запускаемых задач.

## Граница репозитория и сервера

В GitHub находятся код, миграции, универсальные `compose.yaml` и
`compose.storage.yaml`, env-шаблоны с заменителями и общие инструкции. Реальные
имена хостов, IP, пароли, ключи, сертификаты, пути дисков и настройки ресурсов
конкретной установки хранятся только на сервере вне checkout. Туда же относятся
данные, индексы, логи, рабочие скрипты оператора, результаты проверок и архивы истории.

Пример структуры на сервере; все пути ниже условные:

```text
/srv/matrix/
  source/                 # checkout исходников
  config/                 # защищённая конфигурация, вне Git
    runtime.env
    compose.server.yaml
    tls/
  data/                   # постоянные данные
  operations/             # скрипты, проверки, логи и резервные копии оператора
```

Локальный Node-запуск остаётся описан в [README](../README.md): `.env.example`
копируют в локальный `.env`. Для проверки Compose достаточно явного
`--env-file .env.compose.example config --quiet`; запуск контейнеров и доступ к
исходной базе для такой проверки не нужны. Локальный `.env` не является серверной
конфигурацией и не переносится в GitHub.

## Роли, данные и сеть

| Роль | Назначение | Секреты и доступ |
| --- | --- | --- |
| `mysql` | MySQL 8.4, БД `matrix`, каталог `data_base` | Операционный и root-пароли; порт не опубликован |
| `migrate` | `node scripts/migrate.mjs`, однократная миграция | Только операционная MySQL |
| `api` | Node.js 24, `search,catalog,workspace,records` | Операционная MySQL, два API-ключа, TLS, вложения `control` |
| `manticore` | Поиск по готовым индексам | Без исходных DB-паролей; порты не опубликованы |
| `indexer` | Профиль `indexing`, явное добавление новых таблиц | SELECT источника, операционный каталог |
| `catalog-copy` | Профиль `tools`, явное копирование каталога | SELECT источника, INSERT в пустой каталог |

`backend` — внутренняя сеть. У API есть отдельная сеть `edge`, необходимая для
публикации host-порта; исходные credentials в API отсутствуют. Только opt-in задачи
имеют сеть `source` для маршрута к исходному серверу. Это не заменяет права БД:
исходный пользователь должен иметь только SELECT на нужные таблицы.
Задайте реальный адрес в обязательной переменной `SOURCE_MYSQL_HOST`, а имя БД —
в `SOURCE_MYSQL_DATABASE`. `source-db` и `source_data` в примере являются заменителями.
Не используйте `127.0.0.1` для базы на другом хосте.

Порядок запуска: здоровая MySQL → успешная `migrate` → API. API также ждёт здоровую
Manticore. MySQL healthcheck проверяет авторизованный SELECT, Manticore — HTTP SQL
`SHOW TABLES`, API — доступность TCP transport. Прикладные gRPC-проверки описаны ниже.
Условия зависимостей описаны в [документации Compose](https://docs.docker.com/compose/how-tos/startup-order/).

## Подготовка и TLS

1. На сервере создайте защищённый каталог `config` рядом с checkout. Только для
   новой установки скопируйте `.env.compose.example` в `config/runtime.env` и
   замените пароли и ключи уникальными значениями. Задайте абсолютные
   `MATRIX_DATA_ROOT` и `MATRIX_TLS_DIR`, например `/srv/matrix/data` и
   `/srv/matrix/config/tls`. Ограничьте доступ: каталог `config` — 0700,
   `runtime.env` и `compose.server.yaml` — 0600. Переменные поддерживаемых настроек
   задавайте в `runtime.env`, а серверные ограничения ресурсов и прочие изменения
   Compose — в `compose.server.yaml`. Если изменений нет, достаточно `services: {}`.
2. В примере host bind — `127.0.0.1:50051`, TLS отключён для проверки на localhost.
   Перед LAN-доступом получите серверный сертификат с SAN для реального имени/IP.
   Поместите `server.crt`, `server.key` в `MATRIX_TLS_DIR`; этот существующий каталог
   монтируется read-only в `/run/matrix/tls`. Автоматической генерации сертификата нет.
3. В `runtime.env` установите `MATRIX_GRPC_TLS_CERT=/run/matrix/tls/server.crt` и
   `MATRIX_GRPC_TLS_KEY=/run/matrix/tls/server.key`, затем
   `MATRIX_BIND_HOST=<LAN-IP-сервера>`. Обе TLS-переменные задаются вместе.
   API работает как `node` uid/gid 1000: на Linux подойдут владелец `root:1000`,
   каталог 0750 и ключ 0640. Проверьте фактическую доступность файлов из контейнера.
4. Передайте клиентам доверенный CA или публичный сертификат, адрес и поисковый
   ключ. Административный ключ предназначен только для административного клиента.
   Приватный TLS-ключ остаётся на сервере. Ограничьте gRPC LAN/VPN и firewall.

Во всех серверных командах ниже используется одна функция Bash с явными путями:

```bash
SOURCE=/srv/matrix/source
EXTERNAL=/srv/matrix/config
PROJECT=matrix-example

matrix_compose() {
  docker compose --project-directory "$SOURCE" --env-file "$EXTERNAL/runtime.env" \
    -p "$PROJECT" -f "$SOURCE/compose.yaml" -f "$SOURCE/compose.storage.yaml" \
    -f "$EXTERNAL/compose.server.yaml" "$@"
}
matrix_compose config --quiet
```

`--env-file` явно выбирает файл подстановки вместо локального `.env`; относительный
путь к нему зависел бы от текущего каталога. Экспортированные переменные shell
имеют приоритет над `runtime.env`: перед проверкой и запуском уберите старые
одноимённые переменные и случайно включённые `COMPOSE_PROFILES`. Не загружайте
`runtime.env` через `source`. `--project-directory` фиксирует базу относительных
путей Compose, включая build context и bind mounts; даже в серверном override они
считаются от `SOURCE`, поэтому серверные пути задавайте абсолютными. Явные `-f`
исключают автоматическое подключение локального override. `-p` фиксирует выбранную
установку. При каждом новом shell задавайте те же пути, имя проекта и функцию.

Compose передаёт сервисам только явно перечисленные переменные, а не весь
`runtime.env`; исходные credentials не попадают в API. `config` без `--quiet`
выводит секреты, его полный результат храните только в защищённых операционных файлах.

`MATRIX_API_KEY` и `MATRIX_ADMIN_API_KEY` должны отличаться. В первой схеме миграция
и API используют одного операционного пользователя; это не пользователь источника.
Для разделения привилегий при эксплуатации можно подготовить отдельные учётные
записи миграции и чтения каталога с соответствующей настройкой Compose.

Node-клиент MySQL передаёт пароль точно, включая пробелы. При `_PASSWORD_FILE`
удаляется только завершающий перевод строки; не задавайте одновременно значение
пароля и его `_FILE`. Индексатор записывает подключения в Manticore-конфигурацию
и отклоняет управляющие символы, `#`, `{`, `}`, обратную косую черту и пробелы по
краям вместо их экранирования. Это относится и к исходным, и к каталожным DB-настройкам.
Для него доступны `SOURCE_MYSQL_PASSWORD_FILE`/`MYSQL_PASSWORD_FILE` и
`CATALOG_MYSQL_PASSWORD_FILE`: снимаются только завершающие CR/LF, прочие символы
сохраняются и проходят ту же проверку. В текущем Compose используются переменные
паролей; переход на файлы требует их явного подключения к нужным сервисам.

MySQL создаёт БД/пользователя только на пустом data-volume. Изменение пароля в `runtime.env`
не меняет пароль существующего пользователя: ротацию выполняют отдельно в MySQL и
затем обновляют настройки. См. [инициализацию официального образа MySQL](https://github.com/docker-library/docs/blob/master/mysql/README.md#environment-variables).

## Размещение данных на отдельном диске

Базовый `compose.yaml` сохраняет стандартные Docker managed volumes и не требует
`MATRIX_DATA_ROOT`. Opt-in файл `compose.storage.yaml` привязывает все девять томов
к одноимённым подкаталогам `${MATRIX_DATA_ROOT}` через local driver с
`type: none`, `o: bind`. Это включает MySQL, вложения, корень Manticore,
config/state/indexes/runtime/log и private-конфигурацию Manticore.
Корень должен быть абсолютным путём **на Docker-хосте**,
а все подкаталоги должны существовать до создания контейнеров. См.
[named bind volumes](https://docs.docker.com/reference/compose-file/volumes/#driver_opts).

Сначала смонтируйте выбранный большой диск и обеспечьте его доступность после
перезагрузки до запуска Docker. `/srv/matrix/data` — переносимый пример, сам по себе он
не выбирает отдельный диск. Проверьте mountpoint и свободное место до переноса
данных; при недоступном диске не запускайте контейнеры на пустом каталоге системного
раздела. В примере `DATA_ROOT` должен совпадать с `MATRIX_DATA_ROOT` из
`runtime.env`; эта shell-переменная нужна только для подготовки каталогов:

```bash
DATA_ROOT=/srv/matrix/data
sudo install -d -m 0750 "$DATA_ROOT"
findmnt -T "$DATA_ROOT"
df -h "$DATA_ROOT"
# Продолжайте только после проверки целевого диска и запаса свободного места.
sudo install -d -m 0755 \
  "$DATA_ROOT/manticore-root" \
  "$DATA_ROOT/manticore-config" "$DATA_ROOT/manticore-state" \
  "$DATA_ROOT/manticore-indexes" "$DATA_ROOT/manticore-runtime" \
  "$DATA_ROOT/manticore-log"
sudo install -d -m 0700 \
  "$DATA_ROOT/mysql-data" "$DATA_ROOT/manticore-private"
sudo install -d -o 1000 -g 1000 -m 0750 "$DATA_ROOT/control-files"
matrix_compose config --quiet
```

Эти команды предназначены для новых пустых каталогов. Не применяйте подготовку
владельцев к действующему хранилищу. MySQL и Manticore entrypoints подготовят
владельцев своих новых корней при первом запуске; API работает как uid/gid 1000 и
требует заранее доступный `control-files`. При восстановлении сохраняйте владельцев
и права файлов: Manticore entrypoint не исправляет их рекурсивно.

Для отдельной установки используйте уникальное имя проекта через `-p` либо
`COMPOSE_PROJECT_NAME` и отдельный `MATRIX_DATA_ROOT`. Один новый каталог приложения
недостаточен: в базовом файле задано `name: matrix`. Флаг `-p` имеет приоритет, см.
[имя проекта Compose](https://docs.docker.com/compose/how-tos/project-name/).
Разные проекты с одинаковым `MATRIX_DATA_ROOT` всё равно используют одни файлы.
При совместном запуске API также нужен отдельный свободный published port.
Для действующей установки сохраняйте прежние имя проекта и все девять путей томов.
Функция `matrix_compose` подключает оба универсальных файла и внешний серверный
override; при переносе только конфигурации пути данных не меняются.

Добавление override или изменение `MATRIX_DATA_ROOT` **не переносит** существующие
named volumes и не меняет путь уже созданного тома. До запуска проверьте его
`docker volume inspect` и `Options.device`. Для смены размещения подготовьте
согласованную копию/восстановление в новый корень и отдельный проект; не удаляйте
старые тома для принудительного применения настроек. Успешный `config --quiet`
проверяет Compose, но не mountpoint, права, наличие каталогов или содержимое диска.

## Первый старт

На будущем хосте после настройки секретов и TLS:

```bash
matrix_compose config --quiet
matrix_compose build api migrate manticore indexer catalog-copy
matrix_compose up -d
matrix_compose ps -a
matrix_compose logs --tail=100 migrate api manticore
```

`migrate` должен завершиться с кодом 0. Он применяет версии из `migrations`, повторный
запуск пропускает уже применённые версии. После изменения схемы/образа явно выполните
`matrix_compose run --rm migrate` перед обновлением API. Ошибка миграции блокирует
зависимый API; не обходите её ручным запуском процесса сервера.

Manticore-entrypoint готовит каталоги томов и при отсутствии активной конфигурации
вызывает `--bootstrap`. Bootstrap создаёт пустую поисковую конфигурацию без DB-доступа
и исходных credentials, затем запускает `searchd` от пользователя `manticore`.
Существующая активная конфигурация при перезапуске сохраняется. Обычный `up` не
активирует профили `indexing`/`tools` и не выполняет копирование или построение шардов.

`MANTICORE_ACCESS_MODE` принимает `mmap_preread` (по умолчанию) или `mmap` и задаёт
`access_plain_attrs`, `access_blob_attrs`, `access_dict` для генерируемых plain-шардов.
Для индексов, превышающих доступную RAM, и параллельного запуска нескольких установок
рекомендуется `mmap`: файлы читаются по обращению без предварительного прогрева;
первые запросы могут быть медленнее. Doclists/hitlists сохраняют прежние настройки.
См. [режимы доступа Manticore](https://manual.manticoresearch.com/Creating_a_table/Local_tables/Plain_and_real-time_table_settings#Accessing-table-files).
Смена переменной сама по себе не переписывает сохранённую активную конфигурацию;
режим применяется при следующей явной генерации конфигурации индексатором.

Первый старт с пустым `data_base` допустим. Каталог/рабочие таблицы можно проверять
административным RPC, но это ещё не проверка поиска по исходным данным.

## Копирование только каталога

Подготовьте SELECT-пользователя на источнике и задайте `SOURCE_MYSQL_*` в `runtime.env`.
Проверьте правильность пары: настроенный источник, например `source-db/source_data`,
и операционная цель `mysql/matrix`.
После миграции явно выполните:

```bash
matrix_compose run --rm catalog-copy
```

Задача запускает `node scripts/copy_catalog.mjs` в Node-образе с отдельным окружением.
Она читает только перечисленные поля `data_base` через SELECT, сохраняет исходные
ID и отказывается работать с непустым целевым `data_base`. Источник не изменяется.
Копирование не переносит исходные таблицы, полный dump MariaDB, рабочие таблицы или
логи. Идентификатор документа Manticore включает ID каталога, поэтому перенумерация
каталога недопустима при сохранении индексов.

При повторном запуске с непустой целью ожидается отказ. Не очищайте действующий
каталог ради повторного импорта: сначала определите процедуру согласованного
обновления каталога и индексов и сохраните резервную копию.

Для локального Node-запуска вне Compose аналогичная явная команда —
`npm run catalog:copy` после `npm run migrate`; обе читают `.env`, если он существует.
Для источника задайте отдельные `SOURCE_MYSQL_*`, для цели — `MATRIX_MYSQL_*`.

## Персональные ключи устройств

В режиме `shared` клиент использует общий `MATRIX_API_KEY` из закрытого `runtime.env`.
Чтобы перейти на персональные ключи, примените миграции операционной MySQL,
включите TLS и задайте `MATRIX_AUTH_MODE=device` в `runtime.env`. В этом режиме
клиентам выдаются ключи устройств. `MATRIX_ADMIN_API_KEY` используется для
административного API Workspace.

Администратор может выпускать и отзывать ключи командами внутри контейнера API.

```bash
matrix_compose exec api node scripts/access-keys.mjs issue "Имя пользователя"
matrix_compose exec api node scripts/access-keys.mjs list
matrix_compose exec api node scripts/access-keys.mjs logs ID_КЛЮЧА
matrix_compose exec api node scripts/access-keys.mjs revoke ID_КЛЮЧА
```

Передайте пользователю ключ из вывода `issue`. Сервер сохраняет хеш ключа и
показывает его секретное значение только при выпуске. Пользователь вводит адрес
и ключ в Matrix. Первый запрос с действительной подписью привязывает ключ к
устройству. «Проверить соединение» тоже выполняет такой запрос, поэтому
пользователь делает эту проверку на своём компьютере. Для переноса доступа
отзовите прежний ключ и выпустите новый.

Журнал `access_key_logs` связывает запросы с ID ключа. В нём сохраняются время,
модуль, операция, код gRPC и длительность. Попытка использовать привязанный ключ
с действительной подписью другого устройства записывается с кодом `PERMISSION_DENIED`.
Команда `list` показывает ID ключей, `logs`
выводит до 1000 последних событий по указанному ID.

## Веб-админка ключей

Сервис `web-admin` запускается отдельным контейнером из профиля `admin`. В нём
можно выпускать ключи с именем владельца, менять имя выданного ключа и отзывать доступ.
Сводка показывает число запросов, ошибок и использованных ключей за 1, 7 или 30
календарных дней по UTC, включая сегодня. При выборе владельца в сводку входят
запросы по всем ключам с точно таким же именем. В списке ключей по умолчанию
видны действующие привязанные ключи. Фильтр позволяет показать все ключи,
ключи в ожидании привязки или отозванные ключи. В общем журнале и журнале выбранного
ключа доступны фильтры по периоду, операции и результату. Отменённые запросы
выделены отдельным результатом. Перед запуском примените миграции, включая
`007_access_key_log_dates.sql`, которая добавляет индекс по времени событий.

На вкладке «Каталог баз» можно изменять название, описание, дату актуальности,
страну, тип и оценку достоверности существующих записей `data_base`. ID и имя
исходной таблицы показываются для сверки. Следующий поиск показывает сохранённые
название и описание из MySQL при совпадении ID и имени таблицы с опубликованным
каталогом. Для этих изменений переиндексация не требуется.

Тип базы выбирается из справочника в MySQL. Добавляйте новые варианты через
«Каталог баз» → «Добавить тип». Справочник учитывает различия в регистре и пробелах
и блокирует добавление прежних названий объединённых типов. Миграция `012`
заполняет справочник типами из существующего каталога.

Во внешнем `runtime.env` задайте `MATRIX_WEB_ADMIN_SECRETS_DIR` с абсолютным путём
к закрытому каталогу, `MATRIX_WEB_ADMIN_DB_USER` с именем пользователя MySQL и,
при необходимости, `MATRIX_WEB_ADMIN_TLS_DIR` с каталогом сертификатов. Внутри
контейнера TLS использует `/run/matrix/tls/server.crt` и `/run/matrix/tls/server.key`.
Эти пути можно заменить переменными `MATRIX_WEB_ADMIN_TLS_CERT` и
`MATRIX_WEB_ADMIN_TLS_KEY`. Браузер должен доверять CA выбранного сертификата.

По умолчанию порт `8443` привязан к loopback хоста. Для доступа из локальной сети
задайте `MATRIX_WEB_ADMIN_BIND_HOST` с адресом нужного интерфейса и
`MATRIX_WEB_ADMIN_ALLOWED_CIDRS` со списком разрешённых подсетей через запятую.
Внешний порт задаёт `MATRIX_WEB_ADMIN_PUBLISHED_PORT`.

Создайте отдельного пользователя MySQL с правами на ключи, журнал и каталог. Имя и БД
в примере должны совпадать с параметрами вашего контейнера.

```sql
CREATE USER 'matrix_web_admin'@'%' IDENTIFIED BY 'replace-with-random-password';
GRANT SELECT (id, label, created_at, activated_at, revoked_at),
      INSERT (label, key_digest), UPDATE (label, revoked_at)
      ON matrix.access_keys TO 'matrix_web_admin'@'%';
GRANT SELECT ON matrix.access_key_logs TO 'matrix_web_admin'@'%';
GRANT SELECT (id, name_table, name, info, relevance_date, country, type, trust),
      UPDATE (name, info, relevance_date, country, type, trust)
      ON matrix.data_base TO 'matrix_web_admin'@'%';
GRANT SELECT (name, alias_for), INSERT (name)
      ON matrix.catalog_types TO 'matrix_web_admin'@'%';
```

При обновлении примените миграции и выдайте фактическому пользователю веб-админки
права на `data_base` и `catalog_types` из примера. Затем пересоберите и обновите
контейнер `web-admin`.

Сохраните пароль MySQL в `db-password`, а хеш пароля входа в `password.hash` в
закрытом каталоге `MATRIX_WEB_ADMIN_SECRETS_DIR`. Для подготовки хеша на хосте
с Docker можно использовать образ самого сервиса.

```bash
matrix_compose --profile admin build web-admin
umask 077
read -rs -p 'Пароль входа в веб-админку ' web_admin_password
printf '\n'
printf '%s' "$web_admin_password" | docker run --rm -i matrix-web-admin:local \
  node scripts/hash-web-admin-password.mjs > "$MATRIX_WEB_ADMIN_SECRETS_DIR/password.hash"
unset web_admin_password
```

Перед запуском проверьте права обоих файлов и каталога. В обычном Docker на
Linux можно выдать право чтения группе пользователя `node` внутри контейнера.

```bash
web_admin_gid=$(docker run --rm matrix-web-admin:local id -g)
sudo chgrp "$web_admin_gid" "$MATRIX_WEB_ADMIN_SECRETS_DIR" \
  "$MATRIX_WEB_ADMIN_SECRETS_DIR/db-password" "$MATRIX_WEB_ADMIN_SECRETS_DIR/password.hash"
sudo chmod 0750 "$MATRIX_WEB_ADMIN_SECRETS_DIR"
sudo chmod 0640 "$MATRIX_WEB_ADMIN_SECRETS_DIR/db-password" "$MATRIX_WEB_ADMIN_SECRETS_DIR/password.hash"
matrix_compose --profile admin up -d --no-deps web-admin
```

В этом примере переменная `MATRIX_WEB_ADMIN_SECRETS_DIR` также задаётся в текущей
оболочке для записи файла. `--no-deps` подходит, когда MySQL уже работает и миграции
применены. Откройте HTTPS-адрес, заданный при развёртывании. После выпуска ключа
скопируйте его в момент выдачи. В списке остаются ID, название, время создания,
привязки и отзыва, а также журнал операций.

При обновлении существующей установки добавьте право переименования для
пользователя веб-админки в операционной MySQL.

```sql
GRANT UPDATE (label) ON matrix.access_keys TO 'matrix_web_admin'@'%';
```

Соберите образы, примените миграцию и обновите API и веб-админку.

```bash
matrix_compose --profile admin build api web-admin
matrix_compose --profile admin run --rm migrate
matrix_compose --profile admin up -d --no-deps api web-admin
```

## Административный CRUD

Контракт `protos/workspace.proto` описывает сервис `matrix.workspace.v1.Workspace`.
Методы: `ListRows`, `GetRow`, `CreateRow`, `UpdateRow`, `DeleteRow`. Передавайте
административный ключ в metadata `x-api-key` из защищённой конфигурации
административного сервиса. Храните ключ отдельно от тела запроса и аргументов команды.

`resource` допускает только `data_base`, `work_items`, `service_logs`. `Row` имеет
`id:string` и `values:map<string,string>`: даже числа, флаги и JSON передаются строками.
`ListRows` возвращает `rows` и `total:string`; `limit` по умолчанию 100, максимум 1000,
`offset` — `uint32`. Например, тела последовательных запросов для рабочей записи:

```json
{"resource":"work_items","values":{"namespace":"review","name":"batch-1","payload":"{\"status\":\"new\"}"}}
```

Это `CreateRow`; сохраните `id` из ответа. С ним можно вызвать `GetRow`:

```json
{"resource":"work_items","id":"123"}
```

И `UpdateRow`:

```json
{"resource":"work_items","id":"123","values":{"payload":"{\"status\":\"reviewed\"}"}}
```

Для `DeleteRow` используется такое же тело, как для `GetRow`; ответ содержит
`deleted:boolean`. Для `ListRows`:

```json
{"resource":"work_items","limit":100,"offset":0}
```

У `work_items` обязательны непустые `namespace` и `name`; `payload` содержит
сериализованный JSON, при отсутствии получает `{}`. Поля `data_base` перечислены
в `CATALOG_FIELDS` (`node/modules/workspace/resources.mjs`) и соответствуют каталогу
источника. `id` и `name_table` неизменяемы через `UpdateRow`.

Непустой опубликованный `database-catalog.json` резервирует ID баз этой генерации:
удаление или повторное создание записи с таким ID возвращает
`FAILED_PRECONDITION`. После публикации создание любой новой `data_base` требует
явного незарезервированного `id`, чтобы автоинкремент не переиспользовал идентичность.
Название и описание существующей записи поиск читает из MySQL для источников с
совпадающими ID и именем таблицы. Связь с индексом определяется опубликованным
снимком. При недоступности MySQL или отсутствии совпадающей строки поиск берёт
название и описание из снимка.
Для каждой новой исходной таблицы используйте новый свободный ID и новое
`name_table`; идентичность опубликованных таблиц сохраняется в плане, даже если
запись больше не возвращается из каталога. Не переиспользуйте прежние ID или имена.

`service_logs` поддерживает только `ListRows`/`GetRow`. Сервер пишет метаданные
запросов: `module`, `method`, `status_code`, `duration_ms`, `created_at` (и ID строки).
Содержимое исходных строк, payload запросов и API-ключи в этот журнал не записываются.

## Подписи полей в результатах поиска

Миграция `009_search_field_labels.sql` создаёт таблицу `matrix.search_field_labels`
в операционной MySQL и заполняет её текущими подписями. В `field_key` хранится
точное техническое имя из результата, в `label` — подпись для пользователя.
Для добавления или изменения подписи используйте операционную MySQL.

```sql
INSERT INTO matrix.search_field_labels (field_key, label)
VALUES ('extra_number', 'Дополнительный номер') AS incoming
ON DUPLICATE KEY UPDATE label = incoming.label;
```

API читает таблицу при следующем поиске и отправляет справочник в начале
потока с результатами. Поле без подписи показывается под техническим именем.
После перехода на клиент с поддержкой справочника правки не требуют
обновления клиента, перезапуска API или переиндексации Manticore.

## Новые исходные таблицы, индексация и восстановление

Индексатор рассчитан на полностью импортированные неизменяемые исходные таблицы.
Для каждой новой таблицы соблюдайте порядок:

1. Завершите импорт в настроенную внешнюю MariaDB и проверьте данные. Колонка `id`
   должна иметь целочисленный тип и `NOT NULL`, а строки — уникальные положительные
   ID не больше `4294967295`. `AUTO_INCREMENT` не обязателен: индексатор читает
   фактические границы ID. После регистрации таблицу больше не изменяют.
2. Через административный CRUD добавьте запись в `data_base` операционной MySQL
   (`mysql`, БД `matrix`), указав новый свободный `id` и новое `name_table`.
   Не регистрируйте таблицу, пока импорт ещё идёт. Копирование всего каталога через
   `catalog-copy` предназначено только для первоначально пустой цели.
3. Явно выполните `matrix_compose run --rm indexer`. Этот же запуск используется
   для первой сборки и для добавления следующих таблиц; `--clean` не нужен.
4. После успешного завершения проверьте доступность новой таблицы в каталоге поиска
   и поиск по её данным.

Проверьте каталог и источник перед дорогой операцией, затем запустите одну задачу:

```bash
matrix_compose run --rm indexer python3 /app/scripts/build_manticore_indexes.py --help
matrix_compose run --rm indexer python3 /app/scripts/build_manticore_indexes.py --check-config
matrix_compose run --rm indexer
```

Аргументы `run` заменяют весь command сервиса. `--check-config` проверяет конфигурацию
следующего шарда сохранённого плана; при существующем плане новые таблицы он не
обнаруживает. Если плана ещё нет, для его создания нужны каталог и источник.
Это не пробная полная индексация. Не запускайте `--profile indexing up` как обычный старт: этот профиль
специально включает дорогое построение. Не включайте оба профиля через
`COMPOSE_PROFILES` для повседневного `up`.

Индексатор читает каталог из `CATALOG_MYSQL_*` (`matrix`), исходные строки — из
`MYSQL_*`, которым Compose подставляет `SOURCE_MYSQL_*`. При прямом Python-запуске
поддерживаются также aliases `SOURCE_MYSQL_*`. Только исходные таблицы, на которые
ссылается `data_base`, участвуют в плане; операционные `control`, `work_items` и
`service_logs` не перечисляются и не индексируются. Каталог берётся из контейнера
MySQL; метаданные и строки новых таблиц — только из внешней исходной MariaDB.

При каждом явном запуске индексатор сверяет каталог с сохранённым планом и
добавляет новые таблицы и шарды в конец. Старые описания таблиц, границы строк,
номера шардов и готовые файлы сохраняются. Повторный запуск без новых таблиц не
перестраивает готовые шарды. Внутренние изменения уже известных таблиц не
обнаруживаются и не попадают в поиск: для такого обновления нужна отдельная
процедура обслуживания. Автоматического наблюдателя каталога нет.

После проверки шарда `indextool` индексатор обновляет активную конфигурацию,
перезагружает таблицы SQL-запросом через `http://manticore:9308` и ждёт фактической
видимости таблиц. PID namespace, PID-файл и Docker socket с ним не разделяются.
После остановки повторите `matrix_compose run --rm indexer`: готовые шарды и точка
продолжения сохраняются, незавершённый шард будет повторён. Не удаляйте runtime-данные
и не меняйте идентичность каталога при восстановлении.

`index-plan.json` хранит прежние записи и дополняется новыми таблицами.
`database-catalog.json` содержит каталог всего сохранённого плана, включая таблицы,
чьи шарды ещё строятся. Доступность данных определяется опубликованными шардами и
состоянием индексации; каждый шард подключается к поиску после проверки и reload.
План и снимок сохраняют метаданные известных таблиц на момент регистрации.
Удаление строки из операционного `data_base` оставляет её в сохранённом плане и
опубликованном поисковом каталоге. Не меняйте и не переиспользуйте прежние
`id`/`name_table`. Исключение ранее опубликованной таблицы планируйте как отдельное
обслуживание с согласованной резервной копией и проверкой. Очистка действующей
генерации не является способом добавления новых таблиц.

## Тома и резервные копии

| Named volume | Путь | Кто использует |
| --- | --- | --- |
| `mysql-data` | `/var/lib/mysql` | MySQL |
| `control-files` | `/var/lib/matrix/files` | Только API; содержимое вложений `control.files` |
| `manticore-root` | `/var/lib/manticore` | Manticore, indexer; служебный родительский каталог |
| `manticore-config` | `/var/lib/manticore/config` | Manticore, indexer; активный `manticore.conf` |
| `manticore-state` | `/var/lib/manticore/state` | Публичные JSON; API только read-only |
| `manticore-indexes` | `/var/lib/manticore/indexes` | Manticore, indexer |
| `manticore-runtime` | `/var/lib/manticore/runtime` | Только Manticore, включая PID |
| `manticore-log` | `/var/lib/manticore/log` | Manticore, indexer |
| `manticore-private` | `/var/lib/manticore/private` | Только indexer; конфигурация с исходным паролем |

`manticore-state` содержит план `index-plan.json`, прогресс `indexer.json` и
опубликованный каталог `database-catalog.json`. Сохраняйте его вместе с
`manticore-config` и `manticore-indexes`: после `matrix_compose restart` или
`matrix_compose down` и последующего `matrix_compose up -d` они используются
повторно. Entry point не заменяет существующую активную конфигурацию пустым
bootstrap. Команда `matrix_compose down -v` удаляет named volumes; для стандартных
managed volumes это уничтожает MySQL, план и готовые индексы. Не используйте её для
перезапуска, переноса хранилища или применения storage override.

Публичные файлы state имеют права 0644, каталоги 0755 — Node uid 1000 может читать
их независимо от UID Manticore. Private-каталог имеет права 0700, секретные файлы
0600. API не монтирует config/private/indexes/runtime/log. Entry point меняет права
только корней томов; восстановленные файлы должны сохранять владельца Manticore и
права. Не исправляйте доступ через `chmod -R 777`.

Оба Manticore-роли используют один Dockerfile-stage на
`manticoresearch/manticore:29.9.0`, чтобы `searchd`, `indexer`, `indextool` совпадали.
Версия соответствует [официальному Dockerfile](https://github.com/manticoresoftware/docker/blob/master/Dockerfile)
на момент подготовки. Перед выкладкой проверьте доступность тега/архитектуры;
обновляйте и проверяйте обе роли вместе. Для воспроизводимой production-сборки
после проверки можно закрепить digest. Базовый образ объявляет `/var/lib/manticore`
как volume; явный `manticore-root` закрывает этот путь, чтобы Docker не создавал
дополнительный анонимный том. Дочерние тома из таблицы сохраняют отдельные mountpoints;
private-конфигурация с исходным паролем остаётся только в `manticore-private` у indexer.
Дополнительные файлы в родительском каталоге не считаются частью резервной копии.

Для бэкапа остановите indexer и API-запись, сделайте согласованный логический dump
MySQL `matrix` через `mysqldump` из контейнера. Сохраните том `control-files` вместе
с дампом MySQL: оба нужны для восстановления вложений. Затем остановите Manticore и сохраните
config/state/indexes вместе, сохраняя владельцев и права; отдельно сохраните внешний
каталог конфигурации (`runtime.env`, `compose.server.yaml`, `tls/`) и при необходимости
private-конфигурацию в защищённом хранилище. Не включайте
исходную MariaDB в перенос операционной БД. Логи храните по своей политике retention.
Проверьте восстановление на отдельном хосте с той же версией Manticore. `down`
сохраняет named volumes. При storage override отдельно управляйте резервными копиями
и retention host-каталогов: удаление регистрации тома не является удалением этих
каталогов. Храните прежнюю генерацию и резервные копии до подтверждённого
восстановления и завершения согласованного срока отката. Тестовые копии и логи тоже
занимают место; их очистку планируйте отдельно, проверяя абсолютный путь и отсутствие
активных контейнеров, использующих каталог.

### Подготовка переноса существующих индексов

Сначала проверьте Manticore 29.9.0 на копиях нескольких завершённых шардов в отдельном
корне и отдельной конфигурации. Исходные native-службу, конфигурацию и файлы оставьте
без изменений. Не монтируйте действующее хранилище в тестовый контейнер на запись
и не используйте hard links или symlinks на него: весь комплект файлов каждого
выбранного шарда должен быть независимой копией из согласованного снимка/бэкапа.
Для теста нужны отдельные runtime/log и пути только внутри тестового корня.

Проверьте `indextool --check`, загрузку `searchd`, поля/атрибуты, число документов,
контрольные запросы и повторный запуск копии. Версия tools должна совпадать с daemon.
Успешная загрузка файлов подтверждает только проверенные шарды. Она не подтверждает
совместимость API, всего каталога или возможность продолжить старую индексацию.
До переноса всей генерации отдельно сверьте формат документов и ID, `index-plan.json`,
`indexer.json`, `database-catalog.json` и активную конфигурацию с текущим кодом.
Пути native-конфигурации нельзя переносить без адаптации к контейнерным mountpoints;
секреты из неё не должны попадать в публичный state.

Операционные таблицы и вложения переносятся согласованно через dump/restore MySQL
`matrix` и копию `control-files`; каталог сохраняет исходные ID. Сырую директорию
данных внешней MariaDB нельзя подставлять в `mysql-data` MySQL 8.4. Само размещение
Docker-каталогов и проверка копий не выполняют перенос всей базы, полный запуск
production или переключение клиентов. Полный перенос и переключение требуют
отдельного плана после проверки совместимости и восстановления.

## Проверки при выкладке

Из корня checkout до запуска daemon локально доступны проверки шаблонов:

```bash
npm test
python3 -m unittest discover -s tests
docker compose --env-file .env.compose.example config --quiet
docker compose --env-file .env.compose.example --profile indexing --profile tools config --quiet
docker compose --env-file .env.compose.example -p matrix-candidate -f compose.yaml -f compose.storage.yaml config --quiet
docker compose --env-file .env.compose.example -p matrix-candidate -f compose.yaml -f compose.storage.yaml --profile indexing --profile tools config --quiet
```

При подключённом `compose.storage.yaml` незаданная или пустая `MATRIX_DATA_ROOT`
должна завершать `config --quiet` ошибкой; базовая конфигурация от неё не зависит.
Проверьте также, что все девять `Options.device` после создания томов находятся
в выбранном корне. Локальная проверка конфигурации не создаёт томов и контейнеров.

На будущем хосте дополнительно проверьте сборку обоих образов, совпадение версий
Manticore tools/daemon, миграцию на пустой MySQL и повторный запуск, TLS handshake,
gRPC с поисковым/административным ключами и отказ workspace для поискового ключа.
Для существующего поискового smoke-клиента задайте `MATRIX_API_KEY`,
`MATRIX_GRPC_TLS_CA` и запустите
`node scripts/check_grpc.mjs --endpoint <имя-из-сертификата>:50051`.
После явной индексации проверьте поиск, отмену, статус и сохранение шардов после
перезапуска. Проверьте отсутствие published-портов MySQL/Manticore и доступность
только нужного gRPC bind. Эти live-проверки не заменяются успешным `compose config`.

## Расширение API

Таблица `control` и подключение вкладки «Записи» описаны в
[control-records.md](control-records.md). Миграция `002_control.sql` создаёт таблицу,
а `003_control_initiator.sql` добавляет «Инициатор» перед «Исполнитель», сохраняя
существующие записи. Примените миграции до запуска обновлённого API. Содержимое
вложений хранится в отдельном постоянном томе API.

Добавляйте функциональный модуль в `node/modules/<name>` с явной регистрацией через
`register(context)` и собственным ID; подключайте его в едином реестре
`node/modules/index.mjs`, используемом приложением и проверкой конфигурации, затем
добавляйте ID в `MATRIX_MODULES`.
Общие настройки, авторизация и завершение остаются в `node/core`. Публичный контракт
описывайте в protobuf, сохраняя совместимость search/catalog. Новую роль авторизации
проверяйте реальными loopback gRPC-тестами.

Для нового CRUD-ресурса создайте версионированную миграцию и статическое описание
допустимых полей в `node/modules/workspace/resources.mjs`; отделите читаемые и
записываемые поля. При необходимости расширьте валидацию значений и преобразование
строк в `node/infrastructure/mysql/repository.mjs` и добавьте проверки контракта.
Используйте параметризованные запросы репозитория, а не имена таблиц/колонок из
клиентского ввода. Логи остаются append-only для сервера. Добавление операционной
таблицы не даёт ей право участвовать в индексации: индексатор работает только с
явно описанными в каталоге исходными таблицами.
